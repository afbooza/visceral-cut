## Architecture

**Visc** (formerly Visceral Cut — the repo, Vercel project, and `visceral-cut.vercel.app` domain keep the old name) is a mobile-first PWA for personal workout and readiness tracking, built with React 18 + Vite.

- **Single-component app**: The entire UI lives in `src/App.jsx` (~600 lines). There is no component decomposition, routing library, or state management library.
- **View switching**: Navigation between views (dashboard, history, schedule, session, settings) is handled via `useState` — no React Router.
- **Data persistence (local-first)**: All data is written to `localStorage` first (key `"tony-workout-tracker-v2"`, shape `{ logs: {} }`; in-progress session draft under `"tony-workout-draft"`; exercise catalog under `"tony-workout-catalog"`, shape `{ items: { id: exercise } }`; customized program under `"tony-workout-program"`, shape `{ days: { Push: [...], ... }, up }`), then synced in the background to Upstash Redis via Vercel serverless functions in `api/` (`logs.js`, `draft.js`, `catalog.js`, `program.js`). The client sync layer is `src/sync.js`. Redis data is namespaced per account by the email resolved from the bearer token: logs in a hash `logs:<email>` (field = `YYYY-MM-DD` date key), the catalog in a hash `catalog:<email>` (field = exercise id, per-item newer-wins merge), the in-progress draft under key `draft:<email>`, and the program under key `program:<email>` (whole-object newer-wins). A `users` hash (field = email → `{ status, ts }`) holds sign-up requests and approved members (see Auth). (Bare pre-multiuser keys `logs`/`catalog`/`draft`/`program` may still exist in Redis as orphaned backups of the owner's data from before namespacing — nothing reads them.) A local-data ownership marker (`"tony-workout-account"` = email, or `"legacy"` for the raw sync token) guards shared devices: if a *different* Google account signs in, `adoptAccount()` in App.jsx wipes the four local data keys before syncing so one user's history is never merged into another's account; transitions involving `"legacy"` never wipe (the raw token is only ever the owner's).
- **Video uploads**: Catalog exercises accept either a pasted URL (YouTube etc.) or a file uploaded from the device to Vercel Blob (store `visceral-cut-videos`). Uploads go direct-to-Blob from the client (`upload()` from `@vercel/blob/client`, multipart) — `api/upload.js` only mints the client token (auth: bearer token via `clientPayload`, since the blob library issues the token request itself) and handles DELETE for cleanup. Blob paths are per-user: `videos/<blobDir(email)>/<file>` where `blobDir` = email slug + 8-char sha256 prefix, implemented identically in `api/_lib/auth.js` (Node crypto) and `src/sync.js` (crypto.subtle) — keep the two in sync. Upload and DELETE both enforce `ownsBlobPath`: a user can only touch their own directory; flat legacy `videos/<file>` paths (pre-multiuser, and raw-token devices that don't know their email) belong to the owner. Blob files are deleted best-effort when their exercise is deleted or the video is replaced. Uploaded/direct-file videos play in an in-app overlay `<video>`; other links open externally.
- **Auth (multi-user, approval-gated signup)**: Google OIDC (authorization-code flow) with a legacy shared-secret fallback. Signup is self-serve: anyone can complete Google sign-in, but unknown emails are recorded as `{ status: "pending" }` in the Redis `users` hash and bounced back with a `/#pending=<email>` fragment (the app explains they're awaiting approval) — no session is minted until the owner approves them. `api/auth/login.js` redirects to Google; `api/auth/callback.js` exchanges the code, validates ID-token claims (iss/aud/email_verified), then for approved emails mints a 90-day session token (`v1.<base64url payload>.<hmac>`, signed with `SYNC_TOKEN`) handed back via the `/#auth=` URL fragment. The client stores it in localStorage and sends `Authorization: Bearer <token>`. In `api/_lib/auth.js` (underscore dir = not a route; shared Redis client in `api/_lib/redis.js`): `tokenUser()` verifies signature/expiry only → `{ email }`; every route must use the async `requireUser(req)`/`approvedTokenUser(token)`, which additionally checks approval — env-allowlisted emails short-circuit before Redis (owner auth survives Redis outages), everyone else needs `users[email].status === "approved"`. Because approval is re-checked per request, removing a member locks them out immediately (their namespaced data stays; re-approving restores access). "Approved" = in `ALLOWED_EMAIL` (comma-separated; **first entry = owner**, who is also who the raw `SYNC_TOKEN` maps to, and the only admin for `api/users.js`) or approved in the `users` hash. Empty `ALLOWED_EMAIL` = fully open signup, no approval step, no working raw token, no admin. `api/users.js` (owner-only): GET lists requests/members, POST approves (doubles as manual pre-approval of an email that hasn't signed in yet), DELETE denies/revokes (a denied email can request again). The Settings view fetches it when opened — 403 for non-owners keeps the Members card hidden. Blob uploads pass the bearer token via `clientPayload`. Redis credentials stay server-side.
- **Sync semantics**: On load and on "Sync Now", the app pulls remote logs, merges with local (newer `up`/`ts` timestamp wins per date), and pushes any dates the server is missing — this doubles as the one-time migration of pre-existing localStorage history. Every set input saves the draft locally immediately and pushes it to Redis debounced (1.5s), enabling mid-workout recovery via a "Resume" banner.
- **PWA**: Configured via `vite-plugin-pwa` in `vite.config.js` with Workbox service worker caching (JS, CSS, HTML, images, Google Fonts). Targets standalone portrait mode on mobile.
- **Styling**: Inline styles with JS objects throughout — no CSS files, no CSS framework, no Tailwind. Color palette uses dark background (#0e0e0e) with lime accent (#c8f060). Fonts: DM Mono (body) and Bebas Neue (headings) from Google Fonts.

## Domain Logic

- **Workout programs**: Push/Pull/Legs/Core split, each with warmup exercises and 5-6 main exercises. Sets, reps, and weight are logged per exercise. The stock program lives in the `WORKOUTS` constant; a customized program (exercises swapped in, added, or removed via the Plan tab's Program editor) overrides it per day — always resolve via `getProgram(type)`, never read `WORKOUTS` directly for session/history rendering. Added exercises append to the end of the day (keeps existing indices stable); slots can also be removed and reordered (↕ Reorder mode). For logs that record a `names` array, the session view resolves PREV *by name* (`names.indexOf`), so reorders/removals/swaps don't lose or misattribute history; logs from before the names feature can only match by slot index. History is keyed by exercise *index*, so reordering or removing exercises within a day shifts which historical data shows as PREV — renaming in place is safe. Logs saved since the catalog feature also record a `names` array; the session view suppresses PREV for a slot whose name changed, and history/edit views prefer `log.names` for display.
- **Exercise catalog**: User-defined exercises (name, workout type, tracking style weight/bodyweight/time, body focus, sets/reps, suggested weight, description, video URL) managed in the Catalog tab. Swapping one into a program day copies a snapshot into the program — later catalog edits don't retroactively change the program.
- **Schedule**: Fixed 7-day weekly template mixing lift days, cardio, and rest.

## Deployment

Deployed to Vercel. Build command: `npm run build`, output directory: `dist`. Serverless functions in `api/` are deployed automatically by Vercel.

Required env vars (set in Vercel project settings): `SYNC_TOKEN` (legacy shared secret; also the HMAC key for session tokens), `ALLOWED_EMAIL` (comma-separated always-approved emails; first entry = owner/admin for legacy-token/flat-blob attribution and member approval; other users self-serve sign up and wait for owner approval — no env change needed per user), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (OAuth web client with redirect URI `https://visceral-cut.vercel.app/api/auth/callback`; login returns "auth not configured" until set), the Upstash Redis REST credentials (injected by the Vercel Marketplace Upstash integration), and `BLOB_READ_WRITE_TOKEN` (injected by the linked `visceral-cut-videos` Blob store). Local API testing requires `vercel dev` (plain `vite` dev serves only the frontend; the app degrades gracefully to local-only). `vercel dev` gives functions only Development-scoped env vars: `SYNC_TOKEN` and `BLOB_READ_WRITE_TOKEN` exist there, but the Upstash KV vars are Production/Preview-only and marked sensitive — `vercel env pull` writes them as empty strings, so Redis-backed routes 500 locally unless you paste real KV creds (from the Upstash console) into `.env.local`.
